The Difference: Standard vs. Sequential GUIDs
You are completely right that a standard GUID (like a UUIDv4) is essentially random text.

A standard GUID looks like this: 6f9c8b3d-2a1e-4f7c-9b8a-3d2e1f0c9b8a.

Because it is entirely random, a newly generated standard GUID could alphabetically or numerically start with a 1, an A, or an F. It has no concept of time or order.

A sequential GUID (like NEWSEQUENTIALID() in SQL Server, or a UUIDv7) is specifically engineered to fix this.

It combines a random component with a timestamp block at the beginning or end.

The database ensures that every newly generated sequential GUID is guaranteed to be "greater than" the previous one generated by that server instance.

Visually, they look like regular GUIDs, but if you generate five in a row, you’ll notice the first few blocks steadily incrementing (e.g., A001..., A002..., A003...).

What situation forces an insert into the middle of a page?
An insert happens in the middle of a page whenever the Clustered Index Key of your new row falls numerically or alphabetically between values that already exist on a page that is already full.

Here are the specific situations that cause this:

1. Using a Standard (Random) GUID as your Primary Key
If you use standard, random GUIDs, the database treats them like text/binary strings.

Let's say a leaf page is full and contains rows with keys starting from C... through E....

You insert a new row, and the application generates a random GUID starting with D....

Because it's a clustered index, the database must store this row on that specific page between C and E to maintain physical order. Since the page is full, it is forced to do a page split.
